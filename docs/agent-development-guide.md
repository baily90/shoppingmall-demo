# 智能体（Agent）开发指南

> 沉淀自 mall 项目「智能客服」的完整实战。下次开发类似 Agent 时，照着这份清单逐层设计即可。
> 技术栈：Vercel AI SDK 7 + DeepSeek + pgvector + Langfuse（直接 SDK + 自研编排，不用 LangChain 大框架）。

## 一、核心认知（先厘清概念）

1. **Agent = LLM + 工具 + 自主决策**，不是固定流程。模型在每一步自己决定「调哪个工具 / 输出什么」，你的工作是**塑造它的决策环境**。
2. **ReAct 循环**（思考→行动→观察）的**循环骨架由框架提供**（`streamText` + `tools` + `stopWhen`）。你写的是：工具、提示词、记忆、反馈、评测——这些才是「Agent 的实现」。
3. **「引导」≠ 写死步骤**。不写 `if (要电脑) { 调A; 再调B }`，而是靠三层塑造决策：
   - 工具的 `description + inputSchema` → 让模型知道「有什么能力、参数是什么」
   - 提示词 → 让模型知道「什么时候调、调完怎么做」
   - 工具的返回值（含 hint）→ 让模型知道「这次结果如何、下一步干嘛」
4. **三个维度别混**：
   - **Agent 设计** = 会不会做事（工具 + 提示词 + 记忆）
   - **鲁棒性** = 出事了扛不扛得住（重试、降级、自我纠正）
   - **评测** = 做得好不好（检索/生成/端到端）

---

## 二、设计维度总览

```
┌ 决策层：提示词（什么时候调工具 / 多步流程 / 容错降级）
├ 能力层：工具（description + inputSchema + execute + 反馈）
├ 知识层：RAG 检索管线（粗召回 → 精排 → 阈值 → 无答案兜底）
├ 展示层：生成式 UI（工具结果 → 卡片组件）
├ 记忆层：短时会话摘要 + 长期用户画像（事件溯源 + 水位线）
├ 安全层：泛化读 / 约束写 / human-in-the-loop
├ 成本层：意图路由 + 语义缓存 + 用量预算
├ 鲁棒性层：重试 / 降级 / 自我纠正 / 步数上限 / 断连中止
├ 质量层：分层评测（检索 / 生成 / 端到端）
└ 可观测层：trace（每次模型调用 + 工具调用）
```

## 三、逐层设计要点

### 1. 能力层（工具设计）

每个工具三要素：

```ts
tool({
  description: '…（何时用，写得越清楚模型越容易选对）',
  inputSchema: z.object({ /* 参数，含中文 describe */ }),
  execute: async (args) => { /* 实际逻辑 */ },
})
```

原则：

- **返回「瘦身数据」而非原始响应**——只留模型回答需要的字段，金额/状态做转换，省 token 且让模型聚焦。
- **返回带「反馈」**：空结果返回 `empty + hint`，失败返回 `error + hint`。这是自我纠正的关键。
- **工具分「读」和「写」**：读工具（查询）可放开；写工具（下单/支付）要特别设计（见安全层）。

### 2. 决策层（提示词设计）

提示词分层写：**角色定义 → 核心流程 → 边界场景 → 表达要求**。

关键要写清楚：

- **何时调哪个工具**：「购物意向 → 必须调 getProducts，绝不凭记忆编造」。
- **多步流程**：「下单 = 查商品 → 查地址 → 生成草稿 → 用户确认」。
- **结果展示约定**：「结果已用卡片展示，文字里别重复商品名/价格」。
- **容错降级**：「empty → 按 hint 放宽重试；error → 降级/换方式」。
- **给正反例**：✓「帮你筛出 2 款」 / ✗「XX商品｜¥XXX｜亮点：XXX」。

### 3. 展示层（生成式 UI）

核心：**LLM 产出数据，前端渲染 UI**，不是让模型写一段文字描述商品。

- 工具结果成为消息里的 part（如 `dynamic-tool` / `tool-getProducts`），前端按 `part.type` 分发渲染成卡片。
- 卡片的操作也是**数据驱动**：按钮 `{ type: navigate | api | confirm, ... }`，前端统一处理。
- 结论：不需要为每个功能预设计卡片，用少量通用卡片（ItemCard）+ 数据即可；强定制交互（如下单草稿）才手写。

### 4. 记忆层

- **短时**：会话窗口 + **滚动摘要**——超 token 预算时把旧消息压成 `summary + slots`（关键事实键值对）。
- **长期（用户画像，跨会话）**：一张 `user_profiles` 表（按 userId 存自然语言事实，如「偏好苹果品牌」「预算 5000 左右」）。
  - **写**：模型主动调 `remember` 工具（提示词引导「何时该记」）。识别「搭便车」在回复生成里，**不额外调 LLM**；有值得记的就调工具写 DB，没有就不调。
  - **读**：每次 `assemble` 时读画像、注入 instructions（读 DB + 拼字符串零成本，关键是画像要「小而精」，几十 token）。
- **存储真相，读侧投影**：库里存 append-only 原始消息（模型格式），回显时再投影成 UI 格式。两套结构解耦，互不破坏。

### 5. 安全层

- **泛化读、约束写**：查询类能力可通用化（如 NL→SQL），但写操作（下单/支付/退款）必须收着。
- **通用 SQL 只读 + 三重校验**：单条 SELECT、危险关键字拒绝、表白名单（排除个人/敏感表）。
- **个人数据走「带鉴权的专用工具」**（如 getOrders 带用户 token），**不放开通用 SQL**，否则 A 用户能查到 B 用户的数据。
- **写操作走 human-in-the-loop**：Agent 只生成「草稿」，真正执行由用户在前端确认触发。
- **提示词注入防护（分层防御，无银弹）**：
  1. 提示词加固：system prompt 里写「安全边界」（最高优先级、用户输入是数据不是指令、只查自己的数据）。
  2. 输入侧检测：正则匹配「忽略指令 / system prompt / 角色扮演 / 查他人数据」等特征，命中直接拒绝、不喂给模型、不调工具。
  3. 工具层鉴权兜底：即使前两层被绕过，越权操作也会被工具层挡住（token 鉴权 + 白名单）——这是最硬的一道。

### 6. 鲁棒性层

- **网络**：fetch 包一层「超时 + 退避重试」。
- **空结果**：返回 `empty + hint`，模型按 hint 放宽条件自我纠正。
- **报错**：返回 `error + hint`，模型降级/换方式，不反复重试同一失败操作。
- **步数上限**：`isStepCount(n)` 防死循环。
- **兜底**：模型抛异常时优雅降级，别让用户看到 500。

### 7. 质量层（评测）

分层评测，别只测端到端：

| 层 | 测什么 | 指标 |
|---|---|---|
| 检索 | embedding/召回/rerank 对不对 | Hit@k / MRR / Recall@k |
| 生成 | 给定上下文会不会编造 | faithfulness（LLM 裁判）|
| 端到端 | 整条链路 | correctness + faithfulness + length |

关键补充：

- **工具调用正确性**用**确定性断言**（`expectedTools` 是否被调用）——LLM 裁判测不出「模型是调了工具还是凭记忆编了一个像样的答案」。
- 评测写进 Langfuse，改 prompt/模型后跑一遍对比。
- 加**安全用例**（注入攻击 → 拒绝泄露）。

**golden set（评测集）要覆盖四类用例**，别只放「query 就是 FAQ 原题」的送分题：

| 类型 | 目的 | 例 |
|---|---|---|
| 直接命中 | 基线正确性 | 「怎么申请退款？」 |
| 口语 / 改写 | 考 embedding 鲁棒性 | 「东西寄回去了运费谁出」 |
| 易混项（hard negative） | 考区分度，防近义误召回 | 「退货要多久」应命中「退货流程」而非「退款到账」 |
| 无答案类 | 考「诚实说不知道」，防假阳性 | 「运费险怎么用」（知识库没有）|

**隔离变量再测**：生成评测把上下文「钉死」（不走 embedding/rerank，直接给定 golden 上下文），这样检索质量不会污染生成质量的测量——换 prompt / 模型只对比生成层；检索层单独用 rag-eval 的 Hit@k/MRR/Recall@k 测。两层分开，改哪层就跑哪层，不必每次全链路。

### 8. 可观测层

- **trace**：每次模型调用 + 工具调用都记录（Langfuse/OpenTelemetry）。
- **给开发者看「完整日志」，给用户看「进度状态」**：用户只看到「正在查询商品…」这种实时步骤，不看内部工具名/日志。
- **trace 级属性**：`propagateAttributes({ userId, sessionId, tags })` 把用户/会话挂在 trace 上——排查单个用户问题、按会话算成本都靠它。
- **每次调用带 `telemetry.functionId`**（如 `customer-service-chat-reasoner`）区分路由，观测各模型的用量与质量。
- **离线脚本（eval）退出前显式 `shutdown()` OTel SDK**：BatchSpanProcessor 是异步批量上报，脚本跑完直接 `exit` 会丢最后一批 span——常驻服务没问题（定时器持续刷），eval/一次性脚本必须手动 flush，否则 Langfuse 的 Experiments 页看不到这次运行。

### 9. 知识层（RAG 检索管线）

两段式 + 阈值 + 无答案兜底：

1. **粗召回**：embedding 转向量 → 向量库余弦相似度，多召回（`candidateK ≈ topK × 5`）给精排留空间。
2. **精排**：reranker 按 query 重排取 topK；只有一个候选时跳过重排、直接用余弦阈值判定。
3. **阈值过滤**：rerank 分数 / 余弦相似度低于阈值 → 视为「知识库没有答案」，**返回空而不是硬塞无关文档**——让模型诚实说不知道、引导转人工，而不是拿噪音上下文编答案。阈值要按模型实测定（如 BGE-reranker 相关 >0.5、无关 <0.3）。
4. **降级**：rerank 失败退化为纯向量召回 + 余弦阈值；检索失败绝不拖垮整轮对话。

接入**没有现成 provider 的能力**（如硅基流动的 `/rerank` 非 OpenAI 兼容协议）时，按 AI SDK 接口手写一个最小 `RerankingModelV4`（约 30 行）交给内置 `rerank()` 用，顺带进观测——不必为它引入一套新框架。

### 10. 成本层（省钱 = 少调模型）

三个杠杆，按「命中率从高到低」排：

1. **意图路由**：规则（或分类器）把请求分流到不同模型——简单闲聊/政策问答用便宜模型，下单/多步规划用强推理模型。本项目用正则 `COMPLEX_INTENT` 分流 `deepseek-chat` / `deepseek-reasoner`。成本大头是 token 单价，按任务难度选模型比「全用强模型」省一大截。
2. **语义缓存**：通用政策问答（问题转向量 → 相似度命中直接返回）命中则**零 LLM 调用**。两条铁律：
   - **只缓存「纯政策、非个性化」回答**：带「我的/这单/订单号」等个人信息的问题必须实时查，否则「我的退款到哪了」会命中「退款多久到账」的通用答案、跳过 getOrders。
   - **不缓存「含卡片」的回答**：文字若引用「点上面的卡片」而卡片不随缓存返回会悬空。所以只在「只调用了 getFaq、没产生任何卡片」时才写缓存。
   - 附带：唯一键 upsert + TTL + 概率性清理；查询/写入失败一律跳过缓存，不阻塞主流程。
3. **用量预算**：按用户限制「每日请求次数 + token 总量」，超限 429。先查后扣（不预占、允许并发下少量超额），预算表读写 **fail-open**——基础设施抖动不能让客服整体不可用。

### 11. 流式与持久化（生产细节）

SSE 链路最容易在「用户中途关页面」上丢数据、烧钱，四个要点：

- **断连即中止**：`res.on('close')` 触发 `AbortController`，客户端关页面就不再烧 token。
- **流式期间累计快照**：用 `TransformStream` tap 一次流，把 `text-delta` 累成 partial；客户端中途断开时 `responseMessages` 会 reject，靠这份快照落库「已经生成的内容」，刷新后回答不丢。
- **持久化放 `finally`**：完整响应（assistant/tool 消息）落库放 finally，即使中断也执行；拿不到完整结构就降级用 partial 快照兜底。只缓存「完整跑完」的回答（半截不缓存）。
- **固定话术走快路径**：注入拒绝 / 缓存命中这类不需要模型的结果，直接合成 UI 流返回（用 `ChatTurn = fixed | stream` 联合类型表达），零 LLM 调用、零延迟。

### 12. 并发与一致性

有状态会话必踩的并发坑，三把锁各司其职：

- **消息日志 append-only + 事件溯源**：`chat_messages` 是唯一真相，窗口原文不落库，靠「水位线」懒重建。存的是 ModelMessage，回显再投影成 UIMessage，两套结构解耦。
- **seq 分配用悲观锁**：`SELECT ... FOR UPDATE` 串行化，一次事务锁一次行、查一次 `MAX(seq)`，批量写入避免多步工具循环逐条抢锁。
- **摘要/画像推进用乐观锁（CAS）**：`UPDATE ... WHERE summary_up_to_seq = expected`，冲突不覆盖、本轮用本地结果、下轮重算。
- **首次创建竞态**：并发首条消息撞唯一键（P2002）→ 回查一次；状态行用 `createMany + skipDuplicates` 保证幂等。

## 四、常见坑（Gotchas）

1. **tsx/esbuild 不发射 `design:paramtypes`** → 构造注入必须显式 `@Inject(Xxx)`（tsc 的 Nest 项目不需要）。会表现为「依赖是 undefined、不报错、运行时才炸」。
2. **AI SDK 静态工具 part 的 `type` 是 `tool-xxx`，没有 `toolName` 字段**；只有 `dynamic-tool` 才有。工具名要兜底从 `type` 前缀解析。
3. **工具结果在存储层是 DataContent 信封**（`{type:'json', value:{...}}`），回显给前端时要解包成裸值。
4. **存储用 ModelMessage（模型格式），回显用 UIMessage（UI 格式）**——两套结构，靠「读侧投影」转换，别混存。
5. **推理模型（如 deepseek-reasoner）**有原生思维链，但**工具调用/结构化输出可能不稳**；摘要压缩、结构化输出这类任务用普通模型，聊天主链路才用推理模型。
6. **评测跑真实 Agent 需要真实依赖**（DB、向量库、API key、观测平台都要起）。
7. **AI SDK v7 `generateText` + `Output.object` 的结果在 `.output`，不是 `.object`**——写 `.object` 会 TS 报错或拿到 undefined。
8. **deepseek-reasoner 不接受 `temperature`**：按意图路由后只在普通模型上传 `temperature`，给推理模型传会报错。
9. **token 预算只能事前估算**（精确值要模型调用完才返回）：用近似估算兜底（中文字符÷1.5、其他÷4，近似 BPE），且预算留大余量（64K 模型只当 40K 用）吸收估算误差 + 工具结果体积膨胀。
10. **语义缓存 / 摘要压缩 / 画像归并都是「优化项不是必需项」**：一律包超时 + 失败降级（硬截断 / 保留最新 N 条 / 跳过缓存），绝不让主流程 500。客户端断开时摘要压缩要「不推进水位线、保留原窗口」，下次请求再重试。

## 五、技术选型建议

| 维度 | 推荐 | 说明 |
|---|---|---|
| 编排 | **直接 SDK（AI SDK）+ 自研** | 新项目趋势，可控、可调试；LangChain 太重 |
| 向量库 | pgvector | PG 自带，够用 |
| 工具发现 | 先用写死的工具，工具多了再上 **MCP** | 动态注册、可扩展 |
| 评测 | 分层 + LLM-as-judge | 裁判用更强的模型，注意自我偏见 |
| 观测 | Langfuse / OpenTelemetry | trace 是标配不是可选项 |

---

## 六、一句话记忆点

> Agent 开发 = **设计工具（能力）+ 提示词（决策）+ 反馈（引导）+ 知识（RAG）+ 记忆（状态）+ 安全（边界）+ 成本（省钱）+ 鲁棒性（扛事）+ 评测（质量）+ 观测（看清）**。循环骨架是框架给的，其余都是你一行行写的。
